ISSUE #1: PASSWORD LOGIN BROKEN
─────────────────────────────────
File: dashboard/auth.config.ts (lines 297-317)
Severity: CRITICAL
Impact: Users cannot authenticate with credentials
Status: Intentionally unimplemented

Problem:
  validateUserCredentials() function returns null for ALL inputs.
  Password-based authentication is completely non-functional.

Fix Required:
  1. Query database: SELECT * FROM users WHERE email = ?
  2. Hash verification: bcrypt.compare(password, user.password_hash)
  3. Return user on match, null on mismatch

Estimated Time: 2-3 hours


ISSUE #2: XSS IN QUERY PARAMETERS
──────────────────────────────────
File: dashboard/lib/validation/middleware.ts (line 296)
Severity: CRITICAL
Impact: User input rendered without escaping → XSS execution
Status: Query params stored raw without sanitization

Problem:
  Query parameters assigned to queryObject without XSS sanitization.
  If echoed in HTML responses, malicious scripts execute.

Attack:
  /search?q=<img src=x onerror=alert('XSS')>
  → Executes in user's browser
  → Steals session tokens, injects malware

Fix Required:
  1. Apply sanitizeString() to all query params
  2. Add Content-Security-Policy headers
  3. Use templating with auto-escaping

Estimated Time: 1-2 hours


ISSUE #3: SQL INJECTION DETECTION UNUSED
──────────────────────────────────────────
File: dashboard/lib/input-validation.ts (lines 252-266)
Severity: CRITICAL
Impact: Database compromise if queries use string concatenation
Status: Detection function defined but NEVER CALLED

Problem:
  detectSqlInjection() has comprehensive patterns but enforcement missing.
  Unknown if all database queries use parameterized statements.

Fix Required:
  1. Audit ALL database queries for string concatenation
  2. Convert to parameterized/prepared statements
  3. Enforce detectSqlInjection() on all user inputs
  4. Add pre-commit hook to detect raw SQL strings

Estimated Time: 2 hours


ISSUE #4: RATE LIMIT BYPASS VIA MISSING IP
────────────────────────────────────────────
File: dashboard/lib/rate-limiter.ts (line 186)
Severity: CRITICAL
Impact: Denial of Service; shared-quota DoS attack
Status: All headerless requests grouped under 'anonymous' bucket

Problem:
  When x-forwarded-for, x-real-ip headers missing:
  - All requests share single 'anonymous' rate limit key
  - Attacker exhausts shared bucket → blocks legitimate users
  - Users behind proxies all share quota

Attack:
  1. Attacker makes 1000 requests (no IP headers)
  2. Fills bucket: 1000/1000 requests used
  3. Legitimate user without IP header makes 1 request
  4. REJECTED: "Rate limit exceeded"

Fix Required:
  1. REQUIRE IP header; fail request if missing
  2. Support multiple header formats (x-forwarded-for, cf-connecting-ip, etc)
  3. For authenticated users, use user ID (not IP)
  4. Monitor 'anonymous' key usage (alert if >10% traffic)

Estimated Time: 1 hour


ISSUE #5: ERROR MESSAGE INFORMATION DISCLOSURE
────────────────────────────────────────────────
File: dashboard/lib/error-handling.ts (lines 150-164)
Severity: CRITICAL
Impact: Database schema and credentials exposed in responses
Status: Whitelist approach can be bypassed

Problem:
  getSafeErrorMessage() only checks for 'validation'/'invalid' keywords.
  Attacker crafts errors containing these words to leak sensitive data.

Attack:
  throw new Error('Invalid: UNIQUE constraint failed on users.email_unique_idx')
  → Contains word "Invalid" → passes whitelist
  → Database schema exposed: table name, column names, index details

Fix Required:
  1. Switch to BLACKLIST approach (define safe words, reject everything else)
  2. Return generic "Invalid input" for all errors
  3. Log full details server-side; never expose to client
  4. Expand sensitive field filtering: authorization, x-token, api_key, etc

Estimated Time: 1-2 hours
